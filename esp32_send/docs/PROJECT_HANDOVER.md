## 1. 项目用途与交付范围

两块 ESP32-C6 通过 ESP-NOW 互相发送周期报文，各自采集对端报文的 Wi-Fi CSI，在本机计算运动评分并驱动检测灯。运行时无需上位机、路由器或互联网。

目录名 recv/send 是历史命名；现在两个节点都发送、接收、采集和检测。先后上电不会分配主从或收发角色。这是双向业务通信，不代表无线射频同时全双工收发。

本次交接覆盖：

- 硬件接线、运行表现、编译和烧录方法。
- 主要文件、函数、任务及数据流。
- motion_core 特征、基线、阈值、状态机与参数。
- GPIO11 的可续期1.5秒保持机制。
- 已知实现差异、风险点、调试与实机验收步骤。

当前没有人数统计、人员身份识别、距离测量、双端结果融合、结果互传、CSI 存盘或远程配置功能。检测的是链路环境变化，不保证能识别静止人员存在。两端独立建立背景，因此检测时刻和灯态可能不完全一致。

## 3. 硬件与指示灯

### 3.1 接线

每块板使用相同接线：

| 引脚 | 用途 | 接线建议 |
| --- | --- | --- |
| GPIO10 | 呼吸灯 | GPIO10 → 限流电阻 → LED 正极；LED 负极 → 本板 GND |
| GPIO11 | 检测灯 | GPIO11 → 限流电阻 → LED 正极；LED 负极 → 本板 GND |
| GND | 本板 LED 回路地 | 与本板 LED 负极连接 |

GPIO编号不是排针的物理序号。按实际开发板丝印和引脚图确认。代码按高电平点亮设计；使用低有效灯板时需调整驱动极性。可从330Ω限流电阻开始，再按 LED 规格核对。两块板无线通信，使用各自 USB 供电时无需额外串口连接线。

### 3.2 GPIO10 呼吸灯

LEDC 低速模式，定时器0、通道0，5kHz PWM，10位分辨率。任务每20ms把占空比增减16，范围0～1023，理论完整明暗周期约2.56秒。

呼吸灯说明呼吸任务在运行，不能单独证明 Wi-Fi、CSI 或检测算法正常。没有对端时仍会呼吸。

### 3.3 GPIO11 检测灯

80帧预热期间不会由检测逻辑点亮。进入 PASS 且满足续期条件时点亮，最后一次有效续期后保持约1.5秒。期间 CSI 计算继续运行。

断开对端后，没有新的续期，定时器仍可熄灯；但本机算法并没有独立的“链路离线”状态，不能将熄灯解释为确定无人。

## 4. 快速使用与部署

1. 给两块板贴上 recv、send 标签，记录各自 COM 口。
2. 按第3节接线，分别编译并烧录对应工程。不要向两块板烧录同一节点固件，否则固定 MAC 与配对关系会错误。
3. 将两板放在固定位置，天线方向、供电方式尽量稳定。
4. 两板上电后先保持环境静止，等待背景建立；预热按收到并处理的80帧计数，不是固定80ms。理想100帧/秒时约0.8秒，丢包和计算耗时会延长。
5. 在预期检测区域内移动，观察 GPIO11；连续活动可续期，停止后等待最后一次有效判定后的1.5秒。
6. 改变板子位置或天线方向后，建议复位并重新建立背景，再记录检测结果。

### 4.2 配置确认

两个实际 sdkconfig 当前均启用 `CONFIG_ESP_WIFI_CSI_ENABLED=y`。若关闭，main.c 中的编译检查会报错。

实际 sdkconfig 是2MB Flash，sdkconfig.defaults 则写了4MB，开发板定义也预期4MB。过去构建中的“Expected 4MB, found 2MB”是配置不匹配提示，不能作为已读取实体 Flash 容量的证据。接手时应查询实际板卡规格或使用烧录工具读取 Flash ID，再统一配置。本文不擅自修改容量。

sdkconfig.defaults 是默认配置来源，不会保证覆盖已有 sdkconfig。修改后应检查实际生成配置。不要为解决容量告警直接删除所有配置或擦除整片 Flash。

### 4.3 串口现状

应用入口关闭常规日志，CSI_DATA CSV 输出已经删除。ROM、启动程序及异常路径仍可能输出信息，不等于串口完全禁用。

如需排障，可在开发版本中恢复低频日志；对应 UART 配置为115200：

```powershell
pio device monitor --port COM16 --baud 115200
```

仅恢复日志级别不能恢复 CSI CSV。旧上位机脚本需要 CSI_DATA 输入，不能直接连接当前静默固件完成原来的显示功能。

发送提交失败与发送回调失败是不同情况：立即失败的 esp_now_send 不保证产生完成回调，所以 attempts 不一定等于 success+fail。当前发送循环不等待上一包完成，实际接收CSI频率不能直接视为稳定100Hz。

CSI回调直接调用 motion_core，不通过工作队列。该模块使用静态全局数组，只能由单一处理路径串行调用；若后续移到任务，回调中须先复制CSI数据，不能保留驱动回调缓冲区指针延后使用。

## 7. motion_core 算法与接口

### 7.1 接口

- `motion_core_init()`：标记下次有效帧重新初始化。
- `motion_core_update(csi, raw_len, result)`：处理一帧，成功返回true，并填写评分与状态。
- `motion_core_force_clear()`：清除内部PASS状态及连续计数，不清空基线、质量窗口、阈值历史或预热计数。

motion_result_t包含三项特征、motion_score、trigger_threshold、clear_threshold、selected_count、in_warmup、state_changed、state。结果目前在CSI回调中临时使用，没有对外发布。

### 7.2 幅值与窗口

每两个有符号8位CSI数值组成一对：

```text
A[i] = sqrt(raw[2i]^2 + raw[2i+1]^2)
```

仅使用幅值，交换I/Q顺序不改变幅值。当前没有相位校准、RSSI归一化或平均功率判定。

最大306个子载波，即612字节。raw_len<2、空指针会被拒绝；超长数据会截断，奇数长度最后一字节会被忽略，当前没有严格报错。子载波数量变化会重置全部检测历史并重新预热。

质量环形窗口保存最近80帧完整幅值，包括PASS期间的帧。名称 s_static 不意味着里面只有静态背景。第26帧首次计算质量掩码，此后在帧号为20的倍数时更新（40、60、80……）。

### 7.3 稳定子载波筛选

1. 排除两侧各约8%的子载波，边缘数量取整且至少1个。
2. 计算每个内部子载波的均值、总体标准差、CV=标准差/均值。
3. 计算幅值中位数和MAD（绝对偏差中位数），鲁棒尺度为max(1.4826×MAD, 0.001)。
4. 计算窗口内最大标准化偏差 spike_score。
5. 同时满足均值不低于内部均值的约20%分位点、CV≤0.18、spike_score≤6的子载波被选中。
6. 没有任何子载波通过时，回退为全部中间子载波。

不足26帧时初始掩码为全部子载波。该回退会保证常规长度下仍有输入，但不保证质量良好。

### 7.4 基线更新

窗口至少26帧后，每帧用窗口均值作为候选背景：

```text
baseline[i] = (1-alpha) × baseline[i] + alpha × mean(window[:,i])
CLEAR时 alpha = 0.08/3 ≈ 0.026667
PASS时  alpha = 0.015
```

这里使用的是更新前的算法内部状态。PASS期间仍学习背景，因此持续的环境变化可能逐渐被吸收到基线，不适合将PASS解释为永久占用状态。

### 7.5 综合评分

在当前选中子载波集合上计算：

```text
baseline_diff = mean(abs(当前幅值 - 背景幅值))
frame_diff    = mean(abs(当前幅值 - 上帧幅值))
variance_diff = mean(最近最多6帧的各子载波总体方差)
motion_score  = 0.70×baseline_diff + 0.05×frame_diff + 0.25×variance_diff
```

短窗不足3帧时方差项为0。历史存储保留完整子载波索引，计算时应用当前掩码。

### 7.6 自适应阈值

维护最多300个背景分数。预热帧、CLEAR分支处理的帧，以及PASS恢复CLEAR的帧可进入历史；CLEAR分支中最终触发PASS的分数也会进入历史。阈值先计算，再追加本帧分数。

历史少于8项时，触发阈值1.5，恢复阈值0.8；否则：

```text
m = median(score_history)
sigma = max(0.001, 1.4826 × median(abs(score_history-m)))
trigger = max(1.5, m + 3.5×sigma)
clear = min(max(0.8, m + 1.8×sigma), trigger×0.8)
```

因此实际触发阈值可能大于1.5；1.5是最低门槛，不是固定阈值。

### 7.7 内部状态机

前80帧维持CLEAR并学习历史。预热之后，连续2帧score≥trigger进入PASS；在PASS中连续4帧score≤clear恢复CLEAR。没有达到对应阈值时重置对应计数，处于两阈值之间不会自动退出PASS。

这个逐帧状态机始终运行，独立于检测灯定时器。

## 8. 1.5秒续期机制：实际行为与需求边界

当前实现分为“算法状态”和“显示保持状态”，交接时必须区分。

CSI每帧执行motion_core后，满足以下全部条件才更新 s_last_pass_us：

```c
!motion.in_warmup &&
motion.state == MOTION_STATE_PASS &&
motion.motion_score >= motion.trigger_threshold
```

首次满足条件时，点亮GPIO11并启动1.5秒一次性定时器；后续有效帧只更新最后时间戳。定时器回调读取最新时间戳，若尚不足1.5秒，就按剩余时间重新启动；否则置完成标志并熄灯。下一帧有效对端CSI到达时，处理完成标志，调用motion_core_force_clear，然后继续本帧计算。

示例：t=0首次满足，t=0.8秒再次满足，且之后无续期，则灯约在t=2.3秒熄灭。定时器任务调度会带来实际执行延迟。

需要准确理解的限制：

- GPIO11在保持期间不因算法内部CLEAR而立刻熄灭。
- 算法内部仍可在连续4帧低分后先进入CLEAR，早于灯灭。
- 已在内部CLEAR时，孤立一帧score≥trigger尚未形成PASS，不会续期；通常需要连续2帧重新触发。
- 因而当前逻辑不是“只要任何单帧超阈值就续期”，也不是“算法内部只能在1.5秒后进入CLEAR”。
- 无新CSI时定时器仍会熄灯，但内部强制CLEAR要等下一帧。没有单独的离线告警。

以上是代码现状，与此前口头描述的“只有1.5秒后才进入CLEAR”不完全等价。若验收要求内部状态也严格遵守该时间规则，需要后续统一状态机；本文仅记录现状，没有改动固件。

## 9. 参数调整指南

| SCORE_HISTORY_LEN | 300 | 自适应阈值记忆长度 |
| CV_THRESHOLD / SPIKE_Z_THRESHOLD | 0.18 / 6 | 降低通常使筛选更严格，但可能触发回退 |
| MIN_TRIGGER / TRIGGER_K | 1.5 / 3.5 | 提高通常降低灵敏度 |
| MIN_CLEAR / CLEAR_K | 0.8 / 1.8 | 影响内部恢复阈值，不直接替代1.5秒显示机制 |
| BASELINE_ALPHA / PASS_BASELINE_ALPHA | 0.08/3 / 0.015 | 越大背景跟随越快 |
| 综合评分权重 | update函数 / 0.70、0.05、0.25 | 改变特征贡献，需要重新验证阈值 |
| 连续触发 / 恢复帧数 | update函数内常数2 / 4 | 增大可过滤短脉冲但增加响应延迟 |

当前CONFIG_FREERTOS_HZ=100，一tick为10ms。pdMS_TO_TICKS(1)及(5)均取整为0，因此两个启动延时没有有效的1ms/5ms错峰作用，也没有时间同步或时隙协议。发送周期10ms刚好为一个tick；提高频率前应检查换算结果，避免周期变为0。

调参建议一次只改一组参数，保留同一位置、同一动作的基准数据。没有实际CSI到达率记录时，不应将“帧数”直接转换为确定时间。

## 10. 与原上位机算法的关系

算法来源为原上位机脚本 csi_upper_pc.py 的 CsiPreprocessor 与 CsiDetector；板端将其主要逻辑整理为 motion_core。

保留了幅值特征、质量窗口、CV/MAD筛选、基线更新速度、三个评分权重、自适应阈值、80帧预热及2/4帧滞回。

并非逐帧严格等价移植：

- Python达到窗口门槛后每帧重算掩码，C版周期性重算。
- Python的quantile默认插值，C版20%分位点采用向下取整索引。
- Python对选中后的数组保留时间历史；C版保存完整子载波历史，再用当前掩码取值。
- Python对选中数组长度变化会清空短窗；C版仅总子载波数量变化时重置完整检测器。
- Python解析器拒绝奇数长度或大于612字节的数据；C版目前忽略尾字节或截断。
- 当前没有建立C版与Python版同输入逐帧回归测试。

上位机中的GUI、相位图、IQ散点、CSV/JSON保存和事件窗口保存未移植。原脚本位于工程外，移交时需单独打包，经测试的数据和运行参数也应一起保留。

## 11. 已知问题与后续维护重点

### 11.1 已从源码确认

- 过时注释：main.c仍有“CSV输出”“广播peer”“CSI回调翻转运行灯”等描述；实际为静默、单播、独立PWM任务。以执行代码和本文为准。
- Flash配置冲突见第4节，实体容量尚不能由构建警告确定。
- 定时器与CSI回调共享保持标志；并非所有访问都受同一临界区保护。超时回调在释放锁后熄灯，极端边界上可能与新触发点灯交错，存在灯态竞争，需要实机边界测试或后续统一在单一任务处理灯态。
- motion_core在Wi-Fi回调内计算，质量筛选包含排序；编译成功不代表在100Hz输入下满足实时预算。后续应测最大回调耗时和实际接收率。
- xTaskCreate返回值未检查；Wi-Fi初始化后仍需要动态内存，静态RAM占用率不能代表全部运行时内存。
- wifi_csi_init部分失败路径只记录日志后返回，而应用日志关闭，可能出现呼吸灯正常但CSI未开启。
- first_word_invalid未参与输入处理，未显式跳过可能无效的数据；需结合目标芯片CSI格式验证。
- ESP-NOW peer.encrypt=false，设置PMK不等于开启加密；MAC筛选是来源过滤，不是认证。
- 双节点固定地址只适合当前配对；多个同固件节点会重复MAC，没有自动发现或节点管理。

### 11.2 建议的后续工作

优先明确“算法CLEAR”和“显示CLEAR”的验收定义，处理定时器竞争；随后加入低频诊断、任务创建检查、CSI初始化失败提示和输入校验。若实测回调耗时过长，再将CSI复制入有界队列交给计算任务，同时定义队列满时的丢帧策略。任何此类调整均需重新验证检测行为。

## 12. 排障速查

| 现象 | 检查顺序 |
| --- | --- |
| 两灯均不工作 | 供电、复位/下载模式、烧录端口、LED极性与限流电阻、实际GPIO编号 |
| 呼吸正常但始终不触发 | 两端是否烧了不同节点固件、MAC/信道、CSI使能、预热是否完成、阈值是否过高 |
| 后启动节点呼吸异常 | 恢复低频诊断，检查重启/看门狗/初始化失败、任务创建与回调耗时；不能仅凭启动顺序断言原因 |
| 灯持续亮 | 可能持续满足续期条件；检查环境活动、板体晃动、供电变化和motion_score |
| 灯比算法CLEAR更晚灭 | 可能是正常的1.5秒显示保持，参见第8节 |
| 无串口CSI_DATA | 当前设计已关闭CSV输出 |
| 构建报CSI宏未启用 | 检查实际sdkconfig，不只检查defaults |
| Flash容量警告 | 核对实体规格和配置，再统一；不要当作硬件测量结果 |
| 更换开发环境后编译失败 | 核对历史平台/IDF版本与回调签名；未声明跨所有IDF版本兼容 |

建议调试记录：有效CSI帧率、过滤数量、算法返回状态、评分、触发/恢复阈值、选中子载波数、预热标志、最近续期时间、剩余保持时间及空闲堆。当前固件未自动输出这些指标；如需增加，采用低频汇总，避免每帧串口打印。
